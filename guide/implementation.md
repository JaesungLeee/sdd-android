# 구현 단계

breakdown의 작업을 구현하고, 검증하고, 실패하면 치유하며, 검증을 통과한 작업만 체크한다. `init`이 문서 단계와 함께 설치한다. 시작하기 전에 검사 명령을 정한다.

```sh
npx sdd-android impl setup --lint "./gradlew {module}:detekt"   # 기계 검사의 명령. Lint가 없으면 --lint none
```

스택 전제는 Kotlin, Gradle, Jetpack Compose까지다. 아키텍처 패턴(MVI, MVVM 등), DI, 모듈 구조 같은 프로젝트 고유의 규약은 스킬에 없다. constitution에 적어야 구현이 따르고 검증이 잡는다.

## 스킬

| 방식 | 스킬 | 하는 일 |
|---|---|---|
| 진입점 | `impl-orchestrator` | 메인 세션에서 돈다. 배정, 게이트, 기록만 하고 코드를 쓰지 않는다 |
| 디자인 분석 | `design-inspector` | spec의 Figma 노드를 열어 구조, 토큰, 문구, 상태를 뽑는다 |
| 구현 | `create-test` | 테스트 작업. 구현 전에 쓰고 실패(red)를 확인한다 |
| | `create-logic` | 도메인과 데이터 계층 |
| | `create-ui` | 화면, 상태, 디자인 토큰, 공용 컴포넌트. 화면과 상태마다 프리뷰를 만든다 |
| | `create-structure` | 모듈 골격, 빌드 구성, 화면 전환과 DI의 배선 |
| 검증 | `verify-build` | CLI가 돌린 빌드, Lint, 테스트의 실패를 읽어 분류한다 |
| | `verify-ui` | 코드의 값과 Figma의 대조, 기기 캡처와 Figma 스크린샷의 대조 |
| | `verify-principles` | 도구로 판정하지 못하는 constitution 원칙의 위반과 작업에 없는 변경 |
| 치유 | `heal-build` | 빌드와 Lint 실패. import, 타입, null 안전성 같은 기계적 수정만 한다 |
| | `heal-test` | 테스트 실패. 프로덕션 코드의 로직을 고친다. 테스트는 고치지 않는다 |
| 규칙 | `sync-rules` | 구현 단계 밖에서 사용자가 부른다. constitution 원칙의 검사를 detekt, ktlint, Konsist의 규칙으로 옮긴다 |

구현과 치유 스킬은 서브에이전트에서 돌고, 검증 스킬은 쓰기 도구가 없는 읽기 전용 에이전트로 돈다. 검증은 지적만 하고 고치지 않는다.

## 부르는 법

```text
/impl-orchestrator 로그인
/impl-orchestrator 로그인 --all
/impl-orchestrator 로그인 --fix FIX-001
```

- 기본은 사용자 스토리 하나가 끝나면 멈춘다. 체크된 작업, 검증 결과, 미검증 항목, 바꾼 파일을 보고하고 검토와 커밋을 권한다. 다시 부르면 다음 스토리로 간다.
- `--all`을 주면 스토리 사이에서 멈추지 않고 마지막 확인까지 간다. 사람에게 넘기는 경우에는 `--all`이어도 멈춘다.
- 멈추는 단위는 각 스토리의 첫 작업 앞에서 나뉜다. 셋업과 기반 작업은 첫 스토리의 단위에 들어가고, 마지막 스토리 뒤의 마무리 작업은 따로 한 단위다.
- sdd-android는 커밋하지 않는다. 멈출 때마다 검토하고 커밋한다.
- `--fix FIX-001`은 수정 모드다. 구현이 끝난 feature에 `/fix`가 더한 수정 단위만 구현한다(아래 「수정 모드」).

## 수정 모드

`/fix`가 breakdown에 더한 수정 단위(`[FIX-001]`)를 구현한다. 흐름은 같고 범위만 좁다.

- `impl start {feature} --fix FIX-001`. 그 단위가 있고, 체크되지 않은 작업이 모두 그 단위에 있어야 한다. 아니면 거부한다.
- 배정은 그 단위의 작업만 한다. 끝난 작업에는 다시 종류를 주지 않는다.
- 수정 단위가 한 단위다. 단위 검증과 마지막 확인은 체크포인트에 기록된 작업(곧 그 단위의 작업)의 파일과 모듈만 본다. feature 전체를 다시 돌리지 않는다.
- 검증 실패가 단위 밖의 작업을 다시 고칠 작업으로 돌려주면 오케스트레이터는 멈춘다. 수정이 다른 곳을 깨뜨린 것이다.
- 한계: 바뀐 모듈 밖으로 번지는 회귀는 보지 않는다. 화면 사이의 흐름을 보는 검사(E2E)가 없기 때문이다.

## 흐름

1. **착수 게이트**: breakdown이 완료 상태이고 blueprint에 뒤처지지 않아야 한다. 확인 필요면 한 번 묻고, 중단이면 시작하지 않는다.
2. **배정**: 모든 작업에 종류(`test`, `logic`, `ui`, `structure`)를 하나씩 정해 체크포인트에 기록하고 배정표를 보여 준다. 체크된 작업도 뒤의 검증이 체크를 내릴 수 있어 종류가 있어야 한다. 승인은 묻지 않는다. 어느 종류에도 맞지 않거나 두 종류에 걸치는 작업이 있으면 시작하지 않고 breakdown 개정을 안내한다.
3. **디자인 분석**: spec에 Figma 줄이 있으면 `design-inspector`를 한 번 부른다. 열리지 않는 노드와 화면이 아닌 노드는 이때 한꺼번에 묻는다.
4. **작업**: 다음 작업을 받아 종류에 맞는 `create-*`를 부른다.
5. **작업 검증**: `verify-build`를 부른다. 빌드, Lint, 테스트는 CLI가 `impl check`로 직접 돌려 종료 코드로 적는다(「기계 검사」). `ui` 작업이면 `verify-ui`의 값의 대조도 부른다. 테스트 작업은 검증 대기로 두고 넘어간다.
6. **치유**: 실패하면 `heal-*`를 부르거나, 디자인 불일치와 원칙 위반은 차이 목록과 함께 `create-*`로 되돌린다. 다시 검증한다.
7. **체크**: 검증을 통과한 작업을 CLI가 breakdown에 체크한다.
8. **단위 검증**: 스토리가 끝나면 `verify-principles`를 돌리고, UI 작업이 있었으면 캡처의 대조를 돌린다. 실패하면 해당 작업의 체크를 내리고 6으로 간다. 통과하면 멈춘다.
9. **마지막 확인**: 모든 작업이 끝나면 feature 전체에 빌드, Lint, 테스트(`impl check --final`), 원칙 감사, 캡처의 대조를 돌린다. 여기서는 고치지 않는다. 실패가 있으면 대응하는 작업의 체크를 내리고 끝낸다. 없으면 마지막 확인 줄(`FINAL`)을 체크하고 체크포인트를 지운다.

## 기계 검사

빌드, Lint, 테스트의 통과와 실패는 CLI가 정한다. 에이전트가 "통과했다"고 보고하는 것만으로는 체크가 오르지 않는다.

- 명령은 `.sdd-android/config.yaml`의 `impl.checks`에 있다. 커밋하는 설정이라 팀이 같은 검사를 돌린다. `impl setup`이 적고, 손으로 고쳐도 된다.
- `impl setup`은 Gradle 설정(모듈의 빌드 스크립트, `build-logic`과 `buildSrc`의 컨벤션 플러그인)을 읽어 Lint 도구(detekt, ktlint, kotlinter, spotless), 규칙 도구(Konsist), product flavor를 찾고, 설정한 명령과 맞지 않아 보이면 제안한다. Lint를 정하지 않고 부르면 찾은 도구의 명령을 알려 주며 거부한다. flavor가 있는 모듈은 모듈마다 적을 묶음을 보여 준다. 빌드 스크립트는 코드라 찾은 것은 추정이므로, 제안은 적지 않고 사람이 확인해 적는다.

```yaml
impl:
  checks:
    build: "./gradlew {module}:compileDebugKotlin"
    lint: "./gradlew {module}:detekt"                  # Lint 도구가 없으면 none
    test: "./gradlew {module}:testDebugUnitTest {tests}"
    rules: "./gradlew :konsist:test"                   # 선택. Lint 밖의 규칙 도구(Konsist 등)
    # 모듈마다 다른 명령: "*"가 기본이다
    # build:
    #   "*": "./gradlew {module}:compileDebugKotlin"
    #   ":core:domain": "./gradlew {module}:compileKotlin"
```

- `{module}`은 구현 보고(`impl report --modules`)의 모듈이고, 모듈마다 한 번씩 돈다. `{tests}`는 그 작업에 연결된 테스트 작업의 클래스(`--tests '*LoginTest'`)다. 테스트 작업의 경로가 디렉터리면 모듈의 테스트 전체이고, 마지막 확인에서는 비어 있다.
- `impl check {feature} {작업}`이 빌드, Lint, 연결된 테스트를 돌린다. 빌드가 실패하면 테스트는 돌지 않는다. 출력은 `.sdd-android/impl/{feature}/logs/`에 남는다. 결과는 다음 `impl verify`가 가져가 판정한다.
- `impl verify`와 `impl final`은 빌드, Lint, 테스트의 통과를 인자로 받지 않는다. 받는 것은 실패의 지목(다른 작업의 파일)과, 환경 문제로 분류한 빌드·테스트의 건너뜀뿐이다. 둘 다 체크를 올리지 못한다.
- Lint의 건너뜀은 설정의 `lint: none`으로만 된다. 빌드와 테스트는 `none`으로 둘 수 없다.
- `rules`는 constitution 원칙의 도구 규칙 가운데 Lint 명령이 돌리지 않는 것(Konsist의 아키텍처 테스트 등)을 돌린다. 있으면 작업마다와 마지막 확인에서 통과해야 하고, 실패는 원칙 위반처럼 그 작업의 `create-*`로 되돌린다. 그런 도구가 없으면 두지 않는다(`impl setup --rules none`이 지운다).
- **자체 확인**: 구현과 치유 스킬은 넘기기 전에 `impl try {feature} {작업} [--modules :모듈] [--only build,lint,rules,test]`로 한 번 돌려 본다. `impl check`와 같은 명령을 같은 방식으로 돌리지만 체크포인트에 아무것도 적지 않고, 로그는 `logs/try-{작업}-{검사}.log`에 따로 남는다. 스킬은 `./gradlew`를 직접 부르지 않으므로, 프로젝트의 Lint 도구나 flavor가 무엇이든 자체 확인과 판정이 같은 명령으로 돈다. 모듈은 `--modules`가 없으면 그 작업의 구현 보고에 적힌 것이다. 테스트 작업이면 그 테스트를, 구현 작업이면 연결된 테스트를 돈다.
- 마지막 확인은 `impl check {feature} --final`의 결과를 쓴다. 그 뒤 구현 보고가 오거나 체크가 내려가면 결과는 지워지고 다시 돌려야 한다.
- **결과의 신선도**: `impl check`는 돌린 때 작업 경로(breakdown의 작업 줄에 적힌 경로와 함께 돈 테스트 작업의 경로)의 내용 해시를 함께 적는다. `impl verify`와 `impl final`은 지금의 해시와 맞춰 보고, 다르면 그 결과를 버리고 다시 돌리라고 거부한다. 디자인만 다시 적는 때에도 앞서 적힌 빌드·Lint의 통과는 그 사이 코드가 바뀌었으면 쓰지 않는다. 커밋이 아니라 내용으로 보므로 스토리마다 커밋해도 코드가 같으면 같은 결과다. 작업 경로 밖의 파일은 보지 않는다.
- 설정이 없으면 `impl start`가 거부하고 `check`가 경고한다.

주의할 것:
- **이미 있던 Lint 위반**: Lint는 모듈 단위로 돈다. 이번 작업과 무관한 기존 위반이 있으면 모든 작업이 Lint 실패가 된다. detekt의 baseline처럼 기존 위반을 빼는 설정을 먼저 둔다.
- **시간 제한**: 스킬의 셸 명령은 Claude Code의 시간 제한(기본 2분, 최대 10분)을 넘으면 끊긴다. 끊기면 결과가 적히지 않아 체크도 오르지 않는다. 처음 빌드가 오래 걸리는 저장소는 `BASH_DEFAULT_TIMEOUT_MS`와 `BASH_MAX_TIMEOUT_MS`를 늘린다.
- **판정의 한계**: 이 장치는 에이전트가 착각이나 편의로 통과를 적는 것을 막는다. 셸 명령으로 체크포인트를 직접 고치는 것까지 막지는 못한다.

## 원칙의 판정

constitution의 원칙은 검사 줄([문서 형식](documents.md#constitution-원칙의-검사-줄))에 따라 둘로 나뉘어 판정된다.

| 원칙 | 판정 | 언제 |
|---|---|---|
| 도구 줄이 있다 | Lint와 `rules` 명령의 종료 코드(CLI) | 작업마다, 마지막 확인 |
| `감사`이거나 검사 줄이 없다 | `verify-principles`(LLM). 원칙마다 확인한 곳이나 닿지 않는 이유를 적는다 | 단위마다, 마지막 확인 |

- LLM에 기대는 원칙을 줄이려면 `/sync-rules`로 규칙을 만들고 `/constitution`을 다시 실행해 검사 줄을 도구로 바꾼다. 순서는 규칙이 먼저다. 설정에 없는 규칙을 가리키는 검사 줄은 `check`가 오류로 본다.
- 도구 줄이 있는데 Lint가 `none`이고 `rules`도 없으면 그 규칙은 돌지 않는다. `check`가 경고한다.

## 체크의 뜻

- 체크는 그 작업이 자기 검증을 통과했다는 뜻이다. 구현 스킬의 보고만으로는 체크하지 않는다.
- 테스트 작업은 `[until:]`이 가리키는 구현 작업이 끝나 테스트가 통과할 때 그 구현 작업과 함께 체크된다. 그 전의 구현 작업은 빌드와 Lint로만 체크된다.
- 뒤의 검증(테스트, 원칙 감사, 캡처 대조, 마지막 확인)이 실패해 이미 체크된 작업을 다시 고쳐야 하면 체크가 내려간다. 다시 통과하면 올라간다. 사람에게 넘기면 내려간 채 남는다.
- 작업의 체크가 내려가거나 breakdown 개정으로 작업이 더해지면 마지막 확인 줄도 내려간다.
- 구현 완료는 마지막 확인 줄이 체크된 것이다. `status`가 알린다.

## 치유의 상한과 사람에게 넘기기

- 같은 실패에 대한 시도는 **3회**까지다. 같은 실패는 작업 ID와 실패 종류(빌드, 테스트, Lint, 디자인, 원칙)가 같은 것이다. 오류 문구가 달라져도, 그 사이에 검증을 통과한 적이 있어도 같은 실패로 센다.
- 네 번째 시도는 CLI가 거부하고 사람에게 넘긴다. 횟수는 체크포인트에 있어 세션이 바뀌어도 유지된다.
- 다음 경우에도 사람에게 넘긴다. 작업이 `blocked`로 돌아온 경우(범위 밖의 문제), 의존성을 바꿔야 하는 경우, 테스트가 틀렸다고 판단한 경우, 작업이 지정한 파일 밖을 고쳐야 하는 경우, 어느 작업에도 대응하지 않는 실패.
- 넘긴 작업은 사용자가 고친 뒤 다시 부른다. 다시 시도할지 묻고, 승인하면 횟수가 초기화된다.
- 마지막 확인에서 나온 실패는 고치지 않는다. 다시 부르면 체크가 내려간 작업부터 평소의 검증과 치유를 거친다. 어느 작업에도 대응하지 않는 실패는 직접 고치거나 breakdown을 개정해 작업을 더한 뒤 다시 부른다.

## 검증의 건너뜀

환경 문제로 돌리지 못한 검증은 통과가 아니라 건너뜀이다.

| 검사 | 건너뜀으로 체크를 올릴 수 있는가 |
|---|---|
| 빌드, 테스트 | 없다. 환경을 갖춘 뒤 다시 부른다 |
| Lint | 있다. 프로젝트에 Lint 도구가 없을 수 있다 |
| 원칙 감사 | 있다 |
| 디자인(값의 대조, 캡처의 대조) | 있다. Figma 줄이 없거나, 노드가 열리지 않거나, 기기가 없을 때다. 보고에 UI 미검증으로 적힌다 |

마지막 확인은 단위에서 건너뛴 캡처를 한 번 더 시도한다.

## breakdown에 요구하는 것

- 작업마다 경로가 있어야 한다. 구현 스킬은 그 경로 안에서만 쓰고, 검증 실패의 파일을 작업에 대응시키는 데도 쓴다.
- 작업 하나는 종류 하나에 떨어져야 한다. 테스트와 구현, 로직과 화면을 한 작업에 섞지 않는다.
- 테스트 작업은 구현 작업보다 앞에 두고 `[until:]`을 단다. `[until:]`이 있는 작업은 `test`로 배정된다.
- UI 작업에 Figma 노드를 컴포넌트 단위까지 지정하려면 작업 줄에 링크를 적는다. 없으면 스토리의 Figma 줄을 쓴다.

## 체크포인트

- `.sdd-android/impl/{feature}/checkpoint.yaml`. 기계 검사의 로그는 같은 디렉터리의 `logs/`에 있다. 커밋하지 않는다. CLI가 `.sdd-android/impl/` 안에 `.gitignore`를 둔다.
- 배정, 진행 중인 작업의 단계, 바꾼 모듈, 검증 결과, 시도 횟수, 검증 대기인 테스트 작업을 담는다. 완료의 기준은 breakdown의 체크뿐이다.
- 다시 부르면 체크된 작업을 건너뛰고 진행 중이던 작업의 단계에서 이어 간다. 그 사이 코드를 손으로 고쳤을 수 있으므로 검증부터 다시 한다.
- 커밋되지 않으므로 다른 기기에서 이어 가면 남은 작업의 배정을 다시 판단한다. 체크된 작업에는 영향이 없다.
- 마지막 확인이 통과하면 지운다. 실패가 남으면 다음 실행이 이어받는다.

## 실패 기록

CLI가 `docs/specs/{feature}/failures.md`에 덧붙인다. 커밋하는 파일이다.

기록하는 것:
- 두 번 이상 시도한 끝에 치유된 실패
- 3회를 넘겨 사람에게 넘긴 실패
- 치유의 범위를 넘어 사람에게 넘긴 실패
- 어느 작업의 경로에도 맞지 않는 파일의 실패(작업 없음). 내릴 체크가 없어 오케스트레이터가 멈추고 사람에게 넘긴다
- 마지막 확인에서 남은 실패

기록하지 않는 것: 한 번에 치유된 실패, `create-test`의 의도된 실패, 이전부터 있던 실패, 스킬을 단독으로 불렀을 때의 실패, `blocked`로 돌아온 작업, 환경 문제로 검증하지 못한 경우.

항목에는 날짜, 작업 ID, 실패 종류, 증상, 회차별 시도와 결과, 관련 파일, 끝난 상태가 적힌다. 추가만 하고 고치지 않는다.

## 스킬을 따로 부를 때

아홉 스킬은 직접 부를 수 있다. 이때 체크와 체크포인트는 바뀌지 않는다. `create-*`는 단독으로 불려도 착수 게이트를 보고, 뒤처진 breakdown이면 시작하지 않는다. 확인 필요 판정에서는 서브에이전트가 물을 수 없으므로 `impl-orchestrator`로 부르거나 breakdown을 먼저 맞추라고 안내한다.
