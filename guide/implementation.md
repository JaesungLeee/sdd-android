# 구현 단계

`android` extension이 제공하는 구현 단계다. breakdown의 작업을 구현하고, 검증하고, 실패하면 치유하며, 검증을 통과한 작업만 체크한다. 코어만 설치했으면 이 단계는 없다.

```sh
npx mob-sdd init --extension android     # 처음 설치할 때
npx mob-sdd extension add android        # 이미 설치된 저장소에 더할 때
```

스택 전제는 Kotlin, Gradle, Jetpack Compose까지다. 아키텍처 패턴(MVI, MVVM 등), DI, 모듈 구조 같은 프로젝트 고유의 규약은 스킬에 없다. constitution에 적어야 구현이 따르고 검증이 잡는다.

## 스킬

| 방식 | 스킬 | 하는 일 |
|---|---|---|
| 진입점 | `impl-orchestrator` | 메인 세션에서 돈다. 배정, 게이트, 기록만 하고 코드를 쓰지 않는다 |
| 디자인 분석 | `design-inspector` | spec의 Figma 노드를 열어 구조, 토큰, 문구, 상태를 뽑는다 |
| 구현 | `create-test` | 테스트 작업. 구현 전에 쓰고 실패(red)를 확인한다 |
| | `create-logic` | 도메인과 데이터 계층 |
| | `create-ui` | 화면, 상태, 디자인 토큰, 공용 컴포넌트. 화면과 상태마다 프리뷰를 만든다 |
| | `create-structure` | 모듈 골격, 빌드 구성, 화면 전환과 DI의 배선 |
| 검증 | `verify-build` | 바꾼 모듈의 빌드, Lint, 테스트 |
| | `verify-ui` | 코드의 값과 Figma의 대조, 기기 캡처와 Figma 스크린샷의 대조 |
| | `verify-principles` | constitution 위반과 작업에 없는 변경 |
| 치유 | `heal-build` | 빌드와 Lint 실패. import, 타입, null 안전성 같은 기계적 수정만 한다 |
| | `heal-test` | 테스트 실패. 프로덕션 코드의 로직을 고친다. 테스트는 고치지 않는다 |

구현과 치유 스킬은 서브에이전트에서 돌고, 검증 스킬은 쓰기 도구가 없는 읽기 전용 에이전트로 돈다. 검증은 지적만 하고 고치지 않는다.

## 부르는 법

```text
/impl-orchestrator 로그인
/impl-orchestrator 로그인 --all
```

- 기본은 사용자 스토리 하나가 끝나면 멈춘다. 체크된 작업, 검증 결과, 미검증 항목, 바꾼 파일을 보고하고 검토와 커밋을 권한다. 다시 부르면 다음 스토리로 간다.
- `--all`을 주면 스토리 사이에서 멈추지 않고 마지막 확인까지 간다. 사람에게 넘기는 경우에는 `--all`이어도 멈춘다.
- 멈추는 단위는 각 스토리의 첫 작업 앞에서 나뉜다. 셋업과 기반 작업은 첫 스토리의 단위에 들어가고, 마지막 스토리 뒤의 마무리 작업은 따로 한 단위다.
- mob-sdd는 커밋하지 않는다. 멈출 때마다 검토하고 커밋한다.

## 흐름

1. **착수 게이트**: breakdown이 완료 상태이고 blueprint에 뒤처지지 않아야 한다. 확인 필요면 한 번 묻고, 중단이면 시작하지 않는다.
2. **배정**: 체크되지 않은 모든 작업에 종류(`test`, `logic`, `ui`, `structure`)를 하나씩 정해 체크포인트에 기록하고 배정표를 보여 준다. 승인은 묻지 않는다. 어느 종류에도 맞지 않거나 두 종류에 걸치는 작업이 있으면 시작하지 않고 breakdown 개정을 안내한다.
3. **디자인 분석**: spec에 Figma 줄이 있으면 `design-inspector`를 한 번 부른다. 열리지 않는 노드와 화면이 아닌 노드는 이때 한꺼번에 묻는다.
4. **작업**: 다음 작업을 받아 종류에 맞는 `create-*`를 부른다.
5. **작업 검증**: `verify-build`를 부른다. `ui` 작업이면 `verify-ui`의 값의 대조도 부른다. 테스트 작업은 검증 대기로 두고 넘어간다.
6. **치유**: 실패하면 `heal-*`를 부르거나, 디자인 불일치와 원칙 위반은 차이 목록과 함께 `create-*`로 되돌린다. 다시 검증한다.
7. **체크**: 검증을 통과한 작업을 CLI가 breakdown에 체크한다.
8. **단위 검증**: 스토리가 끝나면 `verify-principles`를 돌리고, UI 작업이 있었으면 캡처의 대조를 돌린다. 실패하면 해당 작업의 체크를 내리고 6으로 간다. 통과하면 멈춘다.
9. **마지막 확인**: 모든 작업이 끝나면 feature 전체에 빌드, Lint, 테스트, 원칙 감사, 캡처의 대조를 돌린다. 여기서는 고치지 않는다. 실패가 있으면 대응하는 작업의 체크를 내리고 끝낸다. 없으면 마지막 확인 줄(`FINAL`)을 체크하고 체크포인트를 지운다.

## 체크의 뜻

- 체크는 그 작업이 자기 검증을 통과했다는 뜻이다. 구현 스킬의 보고만으로는 체크하지 않는다.
- 테스트 작업은 `[until:]`이 가리키는 구현 작업이 끝나 테스트가 통과할 때 그 구현 작업과 함께 체크된다. 그 전의 구현 작업은 빌드와 Lint로만 체크된다.
- 뒤의 검증(테스트, 원칙 감사, 캡처 대조, 마지막 확인)이 실패해 이미 체크된 작업을 다시 고쳐야 하면 체크가 내려간다. 다시 통과하면 올라간다. 사람에게 넘기면 내려간 채 남는다.
- 작업의 체크가 내려가거나 breakdown 개정으로 작업이 더해지면 마지막 확인 줄도 내려간다.
- 구현 완료는 마지막 확인 줄이 체크된 것이다. `status`가 알린다.

## 치유의 상한과 사람에게 넘기기

- 같은 실패에 대한 시도는 **3회**까지다. 같은 실패는 작업 ID와 실패 종류(빌드, 테스트, Lint, 디자인, 원칙)가 같은 것이다. 오류 문구가 달라져도, 그 사이에 검증을 통과한 적이 있어도 같은 실패로 센다.
- 네 번째 시도는 CLI가 거부하고 사람에게 넘긴다. 횟수는 체크포인트에 있어 세션이 바뀌어도 유지된다.
- 다음 경우에도 사람에게 넘긴다. 작업이 `blocked`로 돌아온 경우(범위 밖의 문제), 의존성을 바꿔야 하는 경우, 테스트가 틀렸다고 판단한 경우, 작업이 지정한 파일 밖을 고쳐야 하는 경우, 어느 작업에도 대응하지 않는 실패.
- 넘긴 작업은 사용자가 고친 뒤 다시 부른다. 다시 시도할지 묻고, 승인하면 횟수가 초기화된다.
- 마지막 확인에서 나온 실패는 고치지 않는다. 다시 부르면 체크가 내려간 작업부터 평소의 검증과 치유를 거친다. 어느 작업에도 대응하지 않는 실패는 직접 고치거나 breakdown을 개정해 작업을 더한 뒤 다시 부른다.

## 검증의 건너뜀

환경 문제로 돌리지 못한 검증은 통과가 아니라 건너뜀이다.

| 검사 | 건너뜀으로 체크를 올릴 수 있는가 |
|---|---|
| 빌드, 테스트 | 없다. 환경을 갖춘 뒤 다시 부른다 |
| Lint | 있다. 프로젝트에 Lint 도구가 없을 수 있다 |
| 원칙 감사 | 있다 |
| 디자인(값의 대조, 캡처의 대조) | 있다. Figma 줄이 없거나, 노드가 열리지 않거나, 기기가 없을 때다. 보고에 UI 미검증으로 적힌다 |

마지막 확인은 단위에서 건너뛴 캡처를 한 번 더 시도한다.

## breakdown에 요구하는 것

- 작업마다 경로가 있어야 한다. 구현 스킬은 그 경로 안에서만 쓰고, 검증 실패의 파일을 작업에 대응시키는 데도 쓴다.
- 작업 하나는 종류 하나에 떨어져야 한다. 테스트와 구현, 로직과 화면을 한 작업에 섞지 않는다.
- 테스트 작업은 구현 작업보다 앞에 두고 `[until:]`을 단다. `[until:]`이 있는 작업은 `test`로 배정된다.
- UI 작업에 Figma 노드를 컴포넌트 단위까지 지정하려면 작업 줄에 링크를 적는다. 없으면 스토리의 Figma 줄을 쓴다.

## 체크포인트

- `.mob-sdd/impl/{feature}/checkpoint.yaml`. 커밋하지 않는다. CLI가 디렉터리 안에 `.gitignore`를 둔다.
- 배정, 진행 중인 작업의 단계, 바꾼 모듈, 검증 결과, 시도 횟수, 검증 대기인 테스트 작업을 담는다. 완료의 기준은 breakdown의 체크뿐이다.
- 다시 부르면 체크된 작업을 건너뛰고 진행 중이던 작업의 단계에서 이어 간다. 그 사이 코드를 손으로 고쳤을 수 있으므로 검증부터 다시 한다.
- 커밋되지 않으므로 다른 기기에서 이어 가면 남은 작업의 배정을 다시 판단한다. 체크된 작업에는 영향이 없다.
- 마지막 확인이 통과하면 지운다. 실패가 남으면 다음 실행이 이어받는다.

## 실패 기록

CLI가 `docs/specs/{feature}/failures.md`에 덧붙인다. 커밋하는 파일이다.

기록하는 것:
- 두 번 이상 시도한 끝에 치유된 실패
- 3회를 넘겨 사람에게 넘긴 실패
- 치유의 범위를 넘어 사람에게 넘긴 실패
- 마지막 확인에서 남은 실패

기록하지 않는 것: 한 번에 치유된 실패, `create-test`의 의도된 실패, 이전부터 있던 실패, 스킬을 단독으로 불렀을 때의 실패, `blocked`로 돌아온 작업, 환경 문제로 검증하지 못한 경우.

항목에는 날짜, 작업 ID, 실패 종류, 증상, 회차별 시도와 결과, 관련 파일, 끝난 상태가 적힌다. 추가만 하고 고치지 않는다.

## 스킬을 따로 부를 때

아홉 스킬은 직접 부를 수 있다. 이때 체크와 체크포인트는 바뀌지 않는다. `create-*`는 단독으로 불려도 착수 게이트를 보고, 뒤처진 breakdown이면 시작하지 않는다. 확인 필요 판정에서는 서브에이전트가 물을 수 없으므로 `impl-orchestrator`로 부르거나 breakdown을 먼저 맞추라고 안내한다.
