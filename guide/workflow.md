# 워크플로

단계를 어떤 순서로 돌리고, 게이트와 개정이 어떻게 동작하는지 설명한다. 문서의 형식은 [문서 형식](documents.md)에, 명령은 [CLI와 설정 파일](cli.md)에 있다.

## 단계의 순서

```text
constitution ─▶ prd ─▶ spec ─▶ (clarify) ─▶ blueprint ─▶ breakdown ─▶ (analyze) ─▶ implement
```

- constitution과 prd는 프로젝트에 하나씩이다. spec부터는 feature마다 하나씩이다.
- clarify와 analyze는 건너뛸 수 있고 아무 파일도 고치지 않는다.
- 각 단계는 자기 산출물만 고친다. 상위 문서의 문제를 발견하면 고치지 않고 보고한다. 상위 문서를 고치려면 그 단계를 다시 실행한다.
- 대화에서 한 말은 힌트일 뿐이다. 단계의 근거는 앞 단계의 문서에 적힌 것만이다.

## 세션을 여는 곳

세션은 저장소 루트에서 연다. 하위 디렉터리에서 연 세션도 스킬을 찾아 판정을 받지만, Claude Code가 세션을 연 디렉터리 밖의 `docs/`를 쓰지 못해 문서 단계가 끝나지 않는다.

## 착수 게이트

단계 스킬은 시작할 때 CLI의 판정을 받는다. 판정은 세 가지로 처리된다.

| 처리 | 판정 | 뜻 |
|---|---|---|
| 통과 | 일치, PATCH 뒤처짐 | 그대로 진행한다 |
| 확인 필요 | MINOR 뒤처짐, 미기록 변경, 기준 버전 비어 있음 | 사유를 보여 주고 계속할지 한 번 묻는다 |
| 중단 | MAJOR 뒤처짐, 상위 미해결, 상위 미완료, 기준 버전이 상위보다 높음, 상위 문서 없음 | 시작하지 않는다. 어느 단계를 먼저 다시 실행할지 알린다 |

- **뒤처짐**: 상위 문서가 하위 문서의 기준 버전 뒤에 개정됐다. 등급은 상위 문서의 개정 등급을 따른다.
- **미기록 변경**: 버전을 올리지 않고 상위 문서의 본문을 고쳤다. 그 단계를 다시 실행해 개정을 기록한다.
- **상위 미해결**: 상위 문서가 자기 상위에 뒤처져 있다. 위에서부터 푼다.
- **상위 미완료**: 상위 문서가 아직 `draft`다.

게이트는 세 겹이다. 스킬 본문이 판정을 보고 멈추고, CLI의 쓰기 명령이 뒤처진 상태의 완료 기록을 거부하며, 스킬의 hook이 중단 상태에서 문서 쓰기를 막는다. 사용자가 게이트를 건너뛰자고 해도 스킬은 따르지 않는다. hook은 셸 명령으로 쓰는 것까지는 막지 못하지만, 그렇게 쓴 문서는 `check`와 다음 단계의 게이트에서 미기록 변경으로 드러난다.

관계마다 게이트인지 보고만 하는지가 다르다.

| 하위 → 상위 | 처리 |
|---|---|
| spec → prd | 보고만 한다 |
| blueprint → spec | 게이트 |
| blueprint → constitution | 보고만 한다 |
| breakdown → blueprint | 게이트 |
| 구현 → breakdown | 게이트. breakdown이 완료 상태이고 blueprint에 뒤처지지 않아야 한다 |

## 새로 쓰기와 개정

같은 스킬을 다시 부르면 흐름이 달라진다. 흐름은 스킬이 판정에서 읽는다.

- **신규**: 문서가 없다. 템플릿을 복사해 `draft`로 만들고, 채운 뒤 완료를 기록한다. 완료 시점에 `1.0.0`이 된다.
- **작성 중**: `draft` 문서가 있다. 채우는 단계부터 이어 간다.
- **개정**: 완료된 문서가 있다. 기존 문서 위에서 고치고, CLI가 바뀐 곳을 계산하며, 등급을 승인받아 기록한다.
- **병합 충돌**: 해시 파일에 충돌 표시가 남아 있다. 아래 「병합 뒤 정리」를 따른다.

### 개정 등급

| 등급 | 기준 | 하위 문서 |
|---|---|---|
| MAJOR | 확정된 경계가 바뀐다 | 다시 써야 한다. 다음 단계가 중단된다 |
| MINOR | 기존 것을 유지한 채 늘어난다 | 새 내용을 반영해야 할 수 있다. 다음 단계가 확인을 묻는다 |
| PATCH | 뜻이 바뀌지 않는다 | 영향 없음. 다음 단계가 그대로 통과한다 |

- 등급은 에이전트가 근거와 함께 제안하고 사용자가 승인한다.
- prd와 constitution은 항목마다 등급을 매긴다. 항목을 더하거나 지워 목록이 바뀐 것은 항목 밖(`*`)의 PATCH다. 한 항목에만 의존하는 spec은 그 항목의 등급만 따른다.
- 바뀐 곳은 CLI가 계산한다. 에이전트가 지목하지 않은 항목도 바뀌었으면 기록된다.
- 개정에서도 작업 ID, 체크 상태, 폐기 이력, 미정 항목의 문답은 보존된다.

### 영향 없음 확인

상위 문서가 개정됐지만 이 문서를 고칠 것이 없으면, 본문을 바꾸지 않고 기준 버전만 올린다. 버전은 오르지 않는다.

### spec의 체크리스트

spec은 완료 전에 `checklist.md`로 검증한다. 체크되지 않은 항목이 있거나, 검증한 뒤 spec 본문이 바뀌었으면 CLI가 완료 기록을 거부한다.

## 병합 뒤 정리

두 브랜치가 같은 문서를 각각 개정한 뒤 병합하면 frontmatter와 해시 파일이 서로 다른 쪽의 것이 되거나 충돌 표시가 남는다. `check`가 이를 잡는다.

1. 본문의 충돌은 평소처럼 손으로 푼다.
2. 그 문서의 단계 스킬을 다시 부른다. 스킬이 판정에서 병합 충돌을 보고 `doc restore`로 메타데이터와 해시를 `HEAD` 쪽으로 되돌린다.
3. 들어온 변경이 바뀐 곳으로 나오므로 새 개정으로 기록한다.

두 브랜치가 같은 번호로 항목을 만들었으면 `check`가 중복으로 알린다. 들어온 쪽의 항목에 새 번호를 주고, 그 ID에 의존하는 하위 문서를 사용자가 확인한다.

## 갱신

```sh
npx mob-sdd@latest upgrade
```

| 파일의 상태 | 처리 |
|---|---|
| 고치지 않았다 | 새 버전으로 바꾼다 |
| 고쳤고 새 버전에서 바뀌지 않았다 | 그대로 둔다 |
| 고쳤고 새 버전에서도 바뀌었다 | 그대로 두고 새 버전을 `.new`로 옆에 둔다. 직접 합친 뒤 `.new`를 지운다 |
| 새 버전에 없고 고치지 않았다 | 지운다 |
| 새 버전에 없고 고쳤다 | 남기고 알린다 |

- 사용자의 산출물(`docs/`)은 건드리지 않는다.
- 변경 내역을 설치된 버전부터 새 버전까지 보여 준다.
- 내장 확장(`android`)은 함께 올라간다. 로컬 경로에서 설치한 확장은 같은 경로로 다시 `extension add`한다.
- 낮은 버전으로는 내리지 않는다.

## 환경에서 주의할 것

- **`node`를 찾지 못할 때**: 스킬은 로그인 셸이 아닌 셸에서 CLI를 부른다. `.mob-sdd/bin/mob-sdd` 스크립트가 Homebrew, volta, mise, asdf, nvm, fnm의 흔한 위치에서 `node`를 찾는다. nvm과 fnm은 설치된 것 가운데 가장 높은 버전을 쓰고 `.nvmrc`는 보지 않는다.
- **줄바꿈**: 실행 스크립트는 `.mob-sdd/.gitattributes`로 LF를 고정한다. 문서는 CRLF로 체크아웃되어도 판정이 같다.
- **비대화형 실행**: `claude -p`에서 프로젝트 `.mcp.json`의 MCP 서버를 쓰려면 `--mcp-config .mcp.json`을 준다. 승인 대화가 없어 서버가 올라오지 않는다.
- **hook의 수명**: 스킬의 hook은 그 스킬이 끝난 뒤에도 세션에 남는다. 중단 상태의 문서를 같은 세션에서 직접 쓰려 해도 막힌다.
