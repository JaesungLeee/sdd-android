# breakdown 단계

feature 하나의 작업 목록을 만들거나 개정한다. blueprint의 **어떻게**를 **무엇을 어떤 순서로**로 옮긴다. 설계를 새로 하지 않고, 있는 설계를 빠뜨리지 않는다.

{{> input}}

나누는 입력은 `blueprint.md`이고, `spec.md`는 빠진 요구사항이 없는지 보는 기준이다. 사용자가 함께 적은 설명은 순서와 크기를 정하는 힌트로만 쓴다. blueprint에 없는 작업을 만들지 않는다.

{{> scope-guard}}

이 단계에서는 구현하지 않는다. 소스 코드, 빌드 설정, 테스트 파일을 만들거나 고치지 않는다. 기존 코드는 읽기만 한다.

{{> cli}}

## 위치

- **산출물**: `docs/specs/{feature}/breakdown.md`.
- **템플릿**: `.mob-sdd/templates/breakdown.md`. 직접 복사하지 않고 `mob-sdd doc new breakdown {feature}`로 만든다.
- **상위 문서**: 같은 디렉터리의 `blueprint.md`(게이트).
- **참고 문서**: 같은 디렉터리의 `spec.md`, `research.md`, 있으면 `data-model.md`, `contracts/`, `quickstart.md`.

## 쓰는 기준

- 읽는 사람은 작업 하나를 집어 바로 시작하는 개발자다. 작업은 다른 설명 없이 끝낼 수 있을 만큼 구체적이어야 한다.
- 근거 없는 작업을 만들지 않는다. blueprint나 spec에서 가리킬 수 없는 작업이 필요하면 그것은 설계의 누락이므로 만들지 않고 보고한다.
- 설계나 규약의 내용을 작업의 설명에 다시 풀어 쓰지 않는다. 문서와 섹션을 가리킨다.
- 이 문서는 워크플로에서 유일하게 실행 상태(체크)를 담는다. **이 단계는 체크를 올리거나 내리지 않는다.** 다시 쓸 때 체크를 잃지 않는 것이 내용만큼 중요하다.

## 작업 줄의 형식

```text
- [ ] T010 [P] [US1] [until:T014] 로그인 검증의 테스트를 쓴다 `src/auth/login.test.ts`
- [ ] T012 [P] [US1] 사용자 모델을 만든다 `src/models/user.ts`
- [ ] T014 [US1] 로그인 검증을 구현한다 `src/auth/login.ts`
```

표시는 체크, ID, `[P]`, `[US…]`, `[until:…]`, `[dropped]`, 설명의 순서로 적고 없는 것은 건너뛴다.

- **ID**: `T`와 세 자리 번호. 새로 쓸 때는 실행 순서대로 준다. 한 번 준 ID는 바꾸지 않고 지운 번호는 다시 쓰지 않는다.
- **`[P]`**: 병렬로 할 수 있을 때만 단다. 다른 작업과 파일이 겹치지 않고 끝나지 않은 작업에 의존하지 않아야 한다.
- **`[US1]`**: 사용자 스토리 단계의 작업에는 반드시 단다. spec의 스토리 ID와 같다. 셋업, 기반, 마무리 단계의 작업에는 달지 않는다. 한 스토리의 작업은 한곳에 모은다. 다른 스토리를 사이에 두고 같은 스토리의 작업이 다시 나오면 `check`가 오류로 본다(구현 단계가 단위를 이름으로 기록하기 때문이다).
- **`[FIX-001]`**: `/{{skill:fix}}`가 「수정」 섹션에 더한 작업의 수정 단위다. 이 단계가 새로 달지 않는다.
- **경로**: 작업마다 그 작업이 만들거나 고치는 파일을 **줄 끝에** 백틱으로 감싸 하나 이상 적는다. 여러 개면 줄 끝에 이어 적는다. `/`로 끝나면 그 디렉터리 아래 전체다. CLI는 줄 끝에 이어 적힌 백틱만 경로로 읽으므로, 경로 뒤에 다른 글을 붙이지 않는다.
- **순서**: 문서에 적힌 순서가 실행 순서다. 위에서부터 차례로 실행해도 막히지 않게 적는다.
- **마지막 확인 줄**: 문서의 마지막 작업 줄은 `- [ ] FINAL 마지막 확인`이다. feature 전체의 검증을 뜻하며 CLI만 올리고 내린다. 지우거나 옮기거나 체크하지 않는다.

## 테스트 작업

- 테스트 작업을 둘지는 헌법의 원칙, blueprint의 설계, 사용자의 요청으로 정한다. 근거가 없으면 사용자에게 묻는다.
- 테스트 작업은 **대응하는 구현 작업보다 앞에** 두고 `[until:T014]`를 단다. 그 테스트를 통과시키는 마지막 구현 작업의 ID다. 테스트 하나가 구현 작업 여러 개에 걸쳐 있어도 마지막 하나만 가리킨다.
- 연결 표기는 구현 작업이 끝날 때까지 그 테스트의 검증을 기다린다는 뜻이다. 가리키는 작업이 없거나 테스트보다 앞에 있으면 `check`가 오류로 알린다.

## 단계의 구성

작업은 **사용자 스토리 단위로** 묶는다. 스토리 하나를 그것만으로 구현하고 확인할 수 있어야 한다.

1. **셋업**: 프로젝트 초기화와 기본 구조. 이미 있는 프로젝트라 할 것이 없으면 단계를 지운다.
2. **기반**: 여러 스토리가 함께 쓰는 것. 작업마다 어느 스토리가 쓰는지 드러나게 적는다. 한 스토리만 쓰는 것은 그 스토리의 단계에 둔다.
3. **스토리마다 한 단계**: spec의 스토리 순서대로 둔다. 단계마다 목표와 독립 검증의 방법을 적는다. 단계 안에서는 테스트, 모델, 로직, 인터페이스, 통합의 순서를 따른다.
4. **마무리**: 여러 스토리에 걸친 작업. `quickstart.md`가 있으면 그 절차의 실행을 여기에 둔다.

- blueprint의 구성 요소, `data-model.md`의 엔티티, `contracts/`의 계약마다 그것을 만드는 작업이 있어야 한다. 엔티티가 여러 스토리에 쓰이면 가장 이른 스토리나 기반 단계에 둔다.
- 「의존성과 실행 순서」는 사람이 읽는 설명이다. 작업을 더하거나 뺐으면 함께 맞춘다.

## 새로 쓰기

1. `mob-sdd doc new breakdown {feature}`를 부른다.
2. `blueprint.md`와 `spec.md`를 읽고, 있는 부속 산출물을 읽는다. `docs/constitution.md`가 있으면 읽는다.
3. `breakdown.md`를 제자리에서 채운다. 템플릿의 예시 작업을 실제 작업으로 모두 바꾸고, 주석과 쓰지 않는 섹션(폐기된 작업)을 지운다. 「형식」 섹션과 「마지막 확인」 섹션은 남긴다.
4. spec의 요구사항마다 대응하는 작업이 있는지 확인한다. 대응하는 작업을 만들 수 없는 요구사항은 그 사유와 함께 보고에 싣는다.
5. `mob-sdd check`를 불러 작업 줄의 형식을 검사하고, 이 문서에 대한 오류를 모두 고친다.
6. `mob-sdd doc complete breakdown {feature}`를 부른다.
7. 「보고」를 따른다.

## 개정

새 목록을 만들어 갈아 끼우지 않는다. **제자리에서 합친다.**

1. `breakdown.md`를 읽는다. blueprint에서 기준 버전 뒤에 무엇이 바뀌었는지 확인한다.
2. 지금의 blueprint에서 나오는 작업과 기존 작업을 하나씩 맞대어 본다. 같은 작업인지는 ID가 아니라 **무엇을 어느 파일에 만드는가**로 본다.
    - **그대로인 작업**: ID와 체크를 손대지 않는다. 설명을 다듬는 것은 된다. 대상 파일이나 만드는 것이 달라졌으면 같은 작업이 아니다.
    - **새 작업**: 문서에 있는(폐기된 작업을 포함한) 가장 큰 번호의 다음 번호를 주고, 실행할 수 있는 자리에 끼워 넣는다. 문서의 순서와 ID의 순서가 어긋나도 된다. 기존 스토리의 작업이면 그 스토리 섹션 안에 넣는다. 문서 끝에 덧붙이지 않는다.
    - **수정 단위**(`## 수정: FIX-…`): `/{{skill:fix}}`가 더한 것이다. 그 작업은 blueprint에서 나온 것이 아니므로 맞대어 보지 않고 그대로 둔다. blueprint의 개정이 그 수정을 무효로 만들면 다른 작업과 같이 폐기한다.
    - **없어진 작업**: 체크되지 않았으면 지운다. 체크되어 있으면 지우지 않고 「폐기된 작업」 섹션으로 옮겨 `[dropped]`를 달고, 폐기 사유와 이미 들어간 코드를 어떻게 정리할지를 아래에 적는다.
3. 「의존성과 실행 순서」를 맞춘다.
4. `mob-sdd check`로 형식을 검사한다.
5. `mob-sdd doc changes breakdown {feature}`를 불러 바뀌었는지 확인한다. 체크만 달라진 것은 바뀐 것이 아니다. 바뀐 곳이 없으면 「영향 없음 확인」으로 간다.
6. 개정 등급을 근거와 함께 제안하고 사용자의 승인을 받는다.
7. `mob-sdd doc revise breakdown {feature} --grade minor`처럼 승인된 등급으로 기록한다.
8. 「보고」를 따른다.

## 영향 없음 확인

blueprint가 개정되어 이 breakdown이 뒤처졌지만 작업에 고칠 것이 없을 때의 흐름이다.

1. blueprint에서 기준 버전 뒤에 바뀐 것을 읽고, 더하거나 빼거나 고칠 작업이 없는지 확인한다.
2. 확인한 내용을 사용자에게 보여 주고 승인을 받는다.
3. `mob-sdd doc confirm breakdown {feature}`를 부른다. breakdown의 버전은 그대로이고 기준 버전만 올라간다.

{{> revision-grade}}

breakdown에는 하위 문서가 없다. 기준은 **이미 한 구현이 영향을 받는가**다.

- **MAJOR**: 완료된 작업을 폐기한다. 작업을 다시 나눠 완료된 작업의 뜻이 달라진다.
- **MINOR**: 작업을 더한다. 하지 않은 작업을 지우거나 순서를 바꾼다.
- **PATCH**: 설명을 다듬는다. 오타를 고친다.

## 끝내기 전 확인

- [ ] 템플릿의 자리표시자와 예시 작업, 주석이 남아 있지 않다
- [ ] `mob-sdd check`가 이 문서에 대해 오류를 내지 않는다
- [ ] 스토리 단계의 모든 작업에 `[US…]`가 있고, 모든 작업에 경로가 있다
- [ ] 테스트 작업이 구현 작업보다 앞에 있고 연결 표기가 있다
- [ ] 마지막 작업 줄이 `FINAL`이고 체크되어 있지 않다
- [ ] 개정이라면 기존 작업의 ID와 체크가 그대로이고, 폐기한 완료 작업이 사유와 함께 남아 있다
- [ ] 소스 코드와 `spec.md`, `blueprint.md`를 고치지 않았다

## 보고

- breakdown의 경로와 버전, 기준 blueprint 버전.
- 전체 작업의 수와 스토리마다의 작업 수, 스토리마다의 독립 검증 방법.
- 개정이라면 그대로 둔 작업, 더한 작업, 지운 작업, 폐기한 작업의 수와 등급. 폐기가 있으면 사유와 정리해야 하는 코드의 범위.
- 대응하는 작업을 만들지 못한 요구사항, blueprint나 spec에서 발견한 문제.
- 다음 단계: 작업 목록의 순서대로 구현한다.
