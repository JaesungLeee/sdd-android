# constitution 단계

프로젝트의 헌법을 만들거나 개정한다. 헌법은 프로젝트에 하나이고, feature마다 쓰는 blueprint가 이 문서의 원칙을 지켰는지 확인한다.

{{> input}}

이 단계는 입력이 비어 있어도 진행한다. 그때는 「원칙의 후보」에 따라 저장소에서 후보를 찾아 제시한다.

{{> scope-guard}}

{{> cli}}

## 위치

- **산출물**: `docs/constitution.md`. 산출물 디렉터리는 `.sdd-android/config.yaml`의 `docs_dir`을 따른다.
- **템플릿**: `.sdd-android/templates/constitution.md`. 직접 복사하지 않고 `sdd-android doc new constitution`으로 만든다.
- **하위 문서**: `docs/specs/{feature}/blueprint.md`. blueprint는 기준으로 삼은 헌법의 버전을 적는다.

## 현재 상태

!`sh "$(git rev-parse --show-toplevel)/.sdd-android/bin/sdd-android" gate constitution`

위에 판정 대신 명령이 글자 그대로 보이면 `sdd-android gate constitution`을 직접 불러 확인한다.

괄호 안의 값이 이번 실행의 흐름을 정한다.

- **신규**: 헌법이 없다. 「새로 쓰기」를 따른다.
- **작성 중**: 헌법이 `draft`로 남아 있다. 「새로 쓰기」의 2번부터 이어서 한다.
- **개정**: 완료된 헌법이 있다. 「개정」을 따른다.
- **병합 충돌**: 병합으로 헌법의 메타데이터나 해시 기록이 충돌했다. 「병합 뒤 정리」를 따른다.

## 쓰는 기준

- 원칙은 **선언적이고 검증할 수 있게** 쓴다. 설계나 코드를 놓고 지켰는지 어겼는지를 판정할 수 있어야 한다. "가능하면", "되도록" 같은 말을 쓰지 않는다.
- 반드시 지켜야 하는 것과 권장하는 것을 구분해 적는다.
- 원칙마다 근거를 한 줄 적는다. 코드 위치나 문서가 있으면 링크하고, 없으면 사람의 결정이라고 적는다. 링크할 곳이 없다는 이유로 원칙을 빼지 않는다.
- 원칙마다 **검사** 줄을 적는다. 이 원칙을 무엇이 판정하는지다.
    - 도구로 표현할 수 있으면(쓰면 안 되는 API, 의존 방향, 파일 이름 규칙처럼 코드만 보고 기계로 가릴 수 있는 것) `**검사**: 도구 \`규칙 이름\` (설정 파일)`로 적는다. 예: `**검사**: detekt \`ForbiddenImport\` (config/detekt.yml)`. 도구 줄은 여럿 둘 수 있다.
    - 도구로 표현할 수 없으면(책임의 나눔, 상태의 흐름처럼 판단이 필요한 것) `**검사**: 감사`로 적는다. 구현 단계의 원칙 감사가 본다.
    - 도구로 표현할 수 있는지는 에이전트가 제안하고 사용자가 정한다. 도구 줄은 그 규칙이 설정 파일에 **이미 있을 때만** 적는다. `sdd-android check`가 대조해 없으면 오류로 본다. 아직 없는 규칙은 `감사`로 두고, 보고에 도구로 옮길 후보로 적는다. 설정 파일을 만들거나 고치는 것은 이 단계가 아니다(`/{{skill:sync-rules}}`가 한다).
    - 도구 줄이 많을수록 구현 단계가 LLM의 판단에 덜 기댄다. 그렇다고 도구가 원칙의 뜻을 다 담지 못하면 도구 줄과 함께 `감사`를 남기지 않는다. 이때는 원칙을 둘로 나눌지 사용자에게 묻는다.
- 특정 feature에만 해당하는 규칙은 쓰지 않는다. 그것은 그 feature의 blueprint가 정한다.
- 원칙의 수는 사용자가 정한다. 템플릿의 자리 수에 맞추지 않는다.

## 원칙 ID

- 형식은 `P-001`이다. 접두사는 `P`로 고정한다.
- 원칙의 제목을 `### [P-001] 이름` 형태로 쓴다. CLI는 이 제목부터 같은 수준이거나 더 높은 수준의 다음 제목 전까지를 그 원칙으로 보고, 원칙마다 바뀌었는지를 계산한다.
- 한 번 준 ID는 바꾸지 않는다. 제목을 바꿔도 ID는 그대로다. 지운 원칙의 번호는 다시 쓰지 않는다.

## 원칙의 후보

원칙은 두 곳에서 나온다. 어디서 나왔든 **원칙으로 확정하는 것은 사용자다.** 후보를 묻지 않고 문서에 쓰지 않는다.

1. **입력**: 사용자가 적은 원칙. 그대로 후보가 된다.
2. **코드**: 입력이 비어 있거나 사용자가 요청하면 저장소를 훑어 후보를 찾는다. README와 기여 안내, 린트와 포매터의 설정, CI 설정, 테스트의 배치, 디렉터리 구조와 모듈 경계를 본다. 코드를 고치지 않고 읽기만 한다.

후보는 아래 형식으로 한 번에 보여 주고, 원칙으로 올릴 것을 사용자가 고르게 한다.

```markdown
| 후보 | 규칙 | 나온 곳 |
|---|---|---|
| 테스트 우선 | 새 동작은 실패하는 테스트를 먼저 쓴다 | 입력 |
| 계층 경계 | `domain` 모듈은 `data` 모듈을 가져다 쓰지 않는다 | 코드: `domain/build.gradle.kts`의 의존성, `config/detekt.yml`의 `ForbiddenImport` |
```

코드에서 찾은 후보는 지금 그렇게 되어 있다는 관찰일 뿐이다. 팀이 그것을 원칙으로 삼으려는지는 알 수 없으므로 확정된 것처럼 쓰지 않는다.

## 새로 쓰기

1. `sdd-android doc new constitution`을 부른다. 템플릿이 `docs/constitution.md`로 복사된다.
2. 「원칙의 후보」에 따라 후보를 모아 보여 주고 사용자의 선택을 받는다.
3. 선택된 원칙으로 자리표시자를 채운다.
    - **핵심 원칙**: 원칙마다 ID, 이름, 규칙, 근거를 쓴다.
    - **추가 섹션**: 원칙으로 쓰기에는 구체적인 제약(기술 스택, 보안 요구, 개발 절차)이 있을 때만 둔다. 없으면 제목까지 지운다.
    - **거버넌스**: 개정 절차, 준수 확인의 방법, 예외의 처리를 쓴다. 입력에 없으면 사용자에게 묻는다.
    - 다 채운 뒤 템플릿의 주석(`<!-- … -->`)을 지운다.
4. 「끝내기 전 확인」을 통과하면 `sdd-android doc complete constitution`을 부른다. 이 명령이 문서를 완료로 기록하고 버전 `1.0.0`을 준다.
5. 「보고」를 따른다.

## 개정

1. `docs/constitution.md`를 읽는다.
2. 입력이 지목한 부분만 고친다. 지목하지 않은 원칙의 문장을 다듬지 않는다.
    - 새 원칙에는 지금까지 쓴 가장 큰 번호의 다음 번호를 준다. 새 원칙도 「원칙의 후보」의 승인을 거친다.
    - 원칙을 없애면 그 항목을 지운다. 번호는 비워 둔다.
3. `sdd-android doc changes constitution`을 부른다. 바뀐 원칙, 새 원칙, 지워진 원칙이 나온다. 원칙 밖(추가 섹션, 거버넌스)이 바뀌었으면 `*`로 나온다.
    - 바뀐 곳이 없다고 나오면 기록할 개정이 없다. 그 사실을 보고하고 끝낸다.
    - 고치려 하지 않은 원칙이 나오면 원래대로 되돌릴지 사용자에게 묻는다.
4. 나온 항목마다 개정 등급을 근거와 함께 제안하고 사용자의 승인을 받는다.
5. 「끝내기 전 확인」을 통과하면 승인된 등급으로 개정을 기록한다. 등급은 `doc changes`가 낸 항목마다 하나씩, 빠짐없이 준다.

    ```bash
    sdd-android doc revise constitution --grade P-002=major --grade P-006=minor --grade '*=patch'
    ```

6. 「보고」를 따른다.

{{> revision-grade}}

헌법에서의 기준은 다음과 같다.

- **MAJOR**: 원칙을 없앤다. 원칙을 이전과 양립하지 않게 다시 정의한다.
- **MINOR**: 새 원칙이나 섹션을 더한다. 기존 원칙이 요구하는 바를 실질적으로 넓힌다.
- **PATCH**: 표현을 분명하게 한다. 오타를 고친다. 근거의 링크를 고친다. **검사** 줄을 더하거나 바꾼다(원칙이 요구하는 바는 그대로이고 판정하는 수단만 바뀐다).
- 지워진 원칙은 MAJOR, 새 원칙은 MINOR 이상이다. CLI가 이보다 낮은 등급을 거부한다.

## 끝내기 전 확인

- [ ] 템플릿의 자리표시자(`[원칙 이름]`처럼 대괄호 안에 설명이 든 것)와 주석이 남아 있지 않다
- [ ] 모든 원칙에 ID와 근거 한 줄이 있다
- [ ] 모든 원칙에 검사 줄이 있고, 도구 줄의 규칙은 `sdd-android check`가 오류 없이 대조한다
- [ ] 모든 원칙이 사용자가 확정한 것이다
- [ ] 원칙마다 지켰는지 어겼는지를 판정할 수 있다
- [ ] 거버넌스에 개정 절차와 준수 확인의 방법이 적혀 있다
- [ ] 이미 있던 ID가 바뀌거나 지운 번호가 다시 쓰이지 않았다

## 보고

- 헌법의 경로와 버전.
- 신규라면 원칙의 수와, 후보였지만 원칙으로 올리지 않은 것.
- 원칙 가운데 도구로 검사하는 것과 감사하는 것의 수. 도구로 옮길 수 있는데 아직 설정에 규칙이 없어 `감사`로 둔 원칙의 목록.
- 개정이라면 무엇을 더하고 고치고 지웠는지와, 항목마다의 등급.
- `doc revise`가 낸 뒤처진 blueprint의 목록을 그대로 전한다. 헌법과 blueprint의 관계는 보고만 하는 관계라 다음 단계를 막지 않는다. MAJOR나 MINOR로 뒤처진 blueprint는 `/{{skill:blueprint}}`을 다시 실행해 원칙을 다시 확인하기를 권한다.
- 입력에 있었지만 이 단계의 범위가 아니라 하지 않은 일.
- 다음 단계: `/{{skill:prd}}`으로 PRD를 쓰거나, feature를 정해 `/{{skill:spec}}`을 실행한다.
