# heal-test

유닛 테스트 실패를 고친다. `heal-build`와 달리 **프로덕션 코드의 로직 수정을 허용한다.** 대신 테스트는 고치지 않는다. 테스트가 spec과 어긋나 틀렸다고 판단하면 고치지 말고 보고한다.

{{> impl-input}}

인자에서 feature, 테스트 작업 ID, 경로, 실패한 테스트와 메시지를 읽는다. 고치는 파일은 그 테스트가 연결된 **구현 작업**의 경로 안이다(`[until:…]`이 가리키는 작업). 경로는 breakdown에서 읽는다.

{{> impl-scope}}

- 테스트 소스 세트의 파일을 고치지 않는다. 테스트를 통과시키려고 단정을 바꾸거나 테스트를 지우거나 `@Ignore`를 더하지 않는다.
- 구현 작업의 경로 밖을 고쳐야 통과하면 `handed`로 보고한다.

{{> cli}}

## 고치는 방법

1. 실패한 테스트를 읽고 그것이 확인하는 요구사항을 `docs/specs/{feature}/spec.md`에서 찾는다. 테스트의 기대가 spec과 같은지 본다.
    - 같으면 구현이 틀린 것이다. 고친다.
    - 다르면 테스트가 틀린 것이다. 고치지 않고 `handed`로 보고한다. 사용자가 테스트 작업을 다시 돌리게 된다.
    - spec이 정하지 않은 것이면 역시 `handed`다. 지어내서 맞추지 않는다.
2. 구현을 고친다. 설계(blueprint)가 정한 구조 안에서 고친다. 구조를 바꿔야 통과하면 `handed`다.
3. 고친 뒤 실패했던 테스트 클래스만 한 번 돌려 본다: `./gradlew {모듈}:testDebugUnitTest --tests {클래스}`. 통과의 판정은 검증 스킬이 다시 한다. 한 번의 호출은 한 번의 시도다.

## 보고의 형식

```text
상태: fixed | handed
짚은 원인: 한 줄
시도: 무엇을 어떻게 고쳤는가 한 줄
바꾼 파일: 저장소 루트 기준 경로를 쉼표로
돌려 본 결과: 테스트와 결과
넘기는 사유: handed일 때. 테스트가 틀림 | spec에 없음 | 구조 변경 필요 | 범위 밖 파일 가운데 무엇인지와 근거(spec의 위치)
```
