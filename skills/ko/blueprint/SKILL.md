# blueprint 단계

feature 하나의 설계를 만들거나 개정한다. spec의 **무엇을, 왜**를 **어떻게**로 옮긴다. 요구사항을 새로 만들지 않고, 있는 요구사항을 빠뜨리지 않는다.

{{> input}}

설계의 입력은 `spec.md`다. 사용자가 함께 적은 설명은 설계 판단의 힌트로만 쓴다. spec에 없는 요구사항이 필요하다고 판단되면 설계에 넣지 않고 보고하며 `/{{skill:spec}}`의 개정을 권한다.

{{> scope-guard}}

이 단계에서는 구현하지 않는다. 소스 코드, 빌드 설정, 테스트 파일을 만들거나 고치지 않는다. 기존 코드는 읽기만 한다.

{{> cli}}

## 위치

- **산출물**: `docs/specs/{feature}/` 아래의 `blueprint.md`와 `research.md`(필수), 해당할 때만 `data-model.md`, `contracts/`, `quickstart.md`.
- **템플릿**: `.sdd-android/templates/blueprint.md`, `.sdd-android/templates/research.md`. 직접 복사하지 않고 `sdd-android doc new blueprint {feature}`로 만든다. 두 파일이 함께 만들어진다.
- **상위 문서**: 같은 디렉터리의 `spec.md`(게이트), `docs/constitution.md`(보고만. 없어도 된다).
- **하위 문서**: 같은 디렉터리의 `breakdown.md`.

## 쓰는 기준

- 읽는 사람은 이 문서만 보고 구현을 시작하는 개발자다. 무엇을 어디에 어떤 경계로 만드는지가 정해져 있어야 한다.
- 코드를 쓰는 문서가 아니다. 타입의 이름, 시그니처, 모듈 경계까지 정하고 함수의 본문은 구현에 남긴다.
- 기술 환경은 저장소의 코드와 설정에서 확인한 것을 쓴다. 추측하지 않는다.
- 프로젝트의 규약은 요약해 옮기지 않고 그 문서를 링크로 가리킨다.
- spec과 헌법이 충돌하거나 spec끼리 모순되면 설계로 봉합하지 않고 보고한다.
- 근거 없이 빈틈을 지어내지 않는다. 설계가 갈리는 곳은 `TBD:`로 남긴다.

## 부속 산출물

부속 산출물은 자기 버전을 갖지 않고 blueprint의 버전에 속한다.

| 산출물 | 만드는 때 | 고치는 방식 |
|---|---|---|
| `research.md` | 언제나 | **쌓는다.** 기존 항목을 덮어쓰거나 지우지 않는다 |
| `data-model.md` | 이 feature가 데이터를 다룰 때 | 지금의 상태로 대체한다 |
| `contracts/` | 사용자나 다른 시스템에 드러나는 인터페이스가 있을 때 | 지금의 상태로 대체한다. 사라진 계약의 파일은 지운다 |
| `quickstart.md` | 끝에서 끝까지 확인하는 실행 절차가 필요할 때 | 지금의 상태로 대체한다 |

- **research.md**: 결정마다 항목 하나를 두고 결정, 근거, 검토한 대안, 결정한 날을 적는다. 결정이 뒤집히면 그 항목을 지우지 않고 제목에 취소선을 긋고 `재검토됨(날짜)`를 붙인 뒤, 새 결정을 새 번호의 항목으로 더한다. 기각한 이력이 남아야 다음 개정에서 같은 후보를 다시 검토하지 않는다.
- **data-model.md**: 엔티티의 이름, 필드, 관계, 요구사항에서 나온 검증 규칙, 해당하면 상태 전이.
- **contracts/**: 계약마다 파일 하나. 형식은 프로젝트의 종류에 맞춘다(공개 API, 명령의 인자와 출력, 엔드포인트, UI의 상태와 이벤트). 지운 계약의 이름과 사유는 보고에 싣는다.
- **quickstart.md**: 선행 조건, 준비 명령, 실행 명령, 기대 결과. 계약과 데이터 모델의 내용을 복제하지 않고 가리킨다. 구현 코드를 넣지 않는다.
- 만들지 않은 조건부 산출물은 `blueprint.md`의 「부속 산출물」에서 그 줄을 지운다.

## OpenAPI 대조

서버 엔드포인트를 쓰는 인터페이스 계약은 서버의 OpenAPI 문서를 조회한 결과를 근거로 쓴다. 기억이나 추측으로 계약을 적지 않는다. 출처는 `.sdd-android/config.yaml`의 `openapi.sources`이고, 조회는 다음 명령으로 한다.

- `sdd-android openapi operations [--source <이름>] [--filter <텍스트>]`: 출처마다 머리말(출처, 조회 시점, 제목과 버전)과 오퍼레이션 목록을 낸다. `--filter`로 경로, ID, 요약, 태그를 좁힌다.
- `sdd-android openapi show <operationId | "METHOD /path">… [--source <이름>]`: 고른 오퍼레이션만 파라미터, 요청 본문, 응답의 스키마까지 펼친다. 목록 전체를 펼치지 않고 이 feature의 계약에 쓰는 것만 펼친다.

출력이 "출처가 없다."로 시작하면 설정이 없는 것이다. `blueprint.md`의 「인터페이스 계약」 섹션에 "OpenAPI 출처가 설정되어 있지 않다"고 적고 이 절은 끝이다. "그런 출처가 없다"는 `--source`의 이름이 틀린 것이니 이름을 고쳐 다시 부른다. 출처가 있으면:

- 조회한 **출처와 조회 시점**(머리말의 내용)을 `blueprint.md`의 「인터페이스 계약」 섹션에 적는다. 출처가 여럿이면 쓴 것마다 적는다.
- 계약은 `show`의 결과에 맞춘다. 경로, 메서드, 파라미터, 요청과 응답의 필드와 타입이 문서와 같아야 한다. 문서에 없는 필드를 더하지 않는다.
- **대응하는 API가 없는 요구사항**과 **spec과 어긋나는 API**(spec이 요구하는 값을 API가 주지 않거나, 형식이 다르다)는 계약에 억지로 맞추지 않고 보고에 적는다. spec을 고칠지 서버에 요청할지는 사용자가 정한다.
- 머리말이 `조회 실패`인 출처가 있으면 그 사실(출처와 오류)과 **대조하지 못한 계약**의 목록을 같은 섹션에 적는다. 그 계약은 조회 없이 쓴 것임을 표시한다.
- 설정은 고치지 않는다. 출처를 더하거나 바꾸는 것은 사용자가 `sdd-android openapi add`로 한다.

## 설계의 순서

1. **읽기**: `spec.md`를 읽는다. `docs/constitution.md`가 있으면 읽는다. 저장소에서 이 feature가 놓일 곳의 코드와 설정을 읽는다.
2. **기술 컨텍스트**: 확인한 것으로 채운다. 확인하지 못한 것은 "확인 필요"로 적는다.
3. **헌법 준수 확인(앞)**: 헌법이 있으면 원칙마다 이 feature가 지킬 수 있는지 본다. 정당화할 수 없는 위반이 있으면 멈추고 보고한다.
4. **리서치**: "확인 필요"와 선택이 필요한 지점마다 조사하고 `research.md`에 항목으로 적는다. 끝나면 "확인 필요"가 남지 않아야 한다.
5. **설계**: 구조, 구성 요소, 주요 흐름을 정하고 해당하는 부속 산출물을 만든다. spec의 요구사항마다 그것을 맡는 구성 요소가 있어야 한다. 서버 엔드포인트를 쓰는 계약은 「OpenAPI 대조」를 따른다.
6. **헌법 준수 확인(뒤)**: 설계를 놓고 원칙마다 다시 판정해 표를 채운다. 위반이 있으면 「복잡도 추적」에 정당화를 적는다. 정당화할 수 없으면 설계를 고친다.

## 새로 쓰기

1. `sdd-android doc new blueprint {feature}`를 부른다.
2. 「설계의 순서」를 따라 `blueprint.md`와 `research.md`를 제자리에서 채운다. 다 채운 뒤 템플릿의 주석과 쓰지 않는 조건부 섹션을 지운다.
3. 「미정 항목」의 절차를 따른다. 문답은 `blueprint.md` 끝의 「미정 항목」 섹션에 적는다.
4. 「끝내기 전 확인」을 통과하면 `sdd-android doc complete blueprint {feature}`를 부른다.
5. 「보고」를 따른다.

## 개정

1. `blueprint.md`와 `research.md`를 읽는다. spec에서 기준 버전 뒤에 무엇이 바뀌었는지 확인한다.
2. spec의 변경과 입력이 지목한 부분만 고친다. 확정된 설계를 근거 없이 다시 쓰지 않는다. 「설계의 순서」에서 변경이 닿는 단계만 다시 한다.
3. 부속 산출물은 변경이 닿는 것만 고친다. `research.md`의 기존 항목은 지우지 않는다.
4. `sdd-android doc changes blueprint {feature}`를 불러 바뀌었는지 확인한다. 바뀐 곳이 없으면 「영향 없음 확인」으로 간다.
5. 개정 등급을 근거와 함께 제안하고 사용자의 승인을 받는다. 설계를 끝내기 전에는 얼마나 바뀌는지 알 수 없으므로 등급은 고친 뒤에 정한다.
6. 「끝내기 전 확인」을 통과하면 `sdd-android doc revise blueprint {feature} --grade minor`처럼 승인된 등급으로 기록한다.
7. 「보고」를 따른다.

## 영향 없음 확인

spec이나 헌법이 개정되어 이 blueprint가 뒤처졌지만 설계에 고칠 것이 없을 때의 흐름이다.

1. 상위 문서에서 기준 버전 뒤에 바뀐 것을 읽고, 설계의 어느 부분과도 어긋나지 않는지 확인한다. 헌법이 바뀌었으면 「헌법 준수 확인」의 판정이 그대로인지 본다.
2. 확인한 내용을 사용자에게 보여 주고 승인을 받는다.
3. `sdd-android doc confirm blueprint {feature}`를 부른다. blueprint의 버전은 그대로이고 기준 버전만 올라간다.

{{> revision-grade}}

blueprint에서의 기준은 **breakdown의 작업을 다시 나눠야 하는가**다.

- **MAJOR**: 모듈 경계, 인터페이스 계약, 구조 결정이 바뀐다. 헌법 준수 확인의 판정이 뒤집힌다. 작업 목록을 다시 짜야 한다.
- **MINOR**: 기존 설계를 둔 채 구성 요소, 계약, 엔티티를 더한다. `TBD:`로 남겨 둔 선택을 확정한다. 작업이 더해질 뿐 기존 작업의 뜻은 그대로다.
- **PATCH**: 표현을 분명하게 한다. 오타를 고친다. 링크를 고치거나 근거를 보탠다.
- 부속 산출물만 바뀌고 `blueprint.md`의 본문이 바뀌지 않으면 CLI는 바뀐 곳이 없다고 낸다. 그 변경이 작업에 영향을 준다면 `blueprint.md`의 설계에도 그 변경을 적어 개정으로 기록한다.

## 끝내기 전 확인

- [ ] 템플릿의 자리표시자와 주석, "확인 필요"가 남아 있지 않다
- [ ] spec의 모든 요구사항에 그것을 맡는 구성 요소가 있다
- [ ] spec에 근거가 없는 요구사항이 설계에 없다
- [ ] 헌법이 있다면 원칙마다 판정이 적혀 있고, 위반에는 정당화가 있다
- [ ] `research.md`의 기존 항목이 지워지지 않았다
- [ ] 「부속 산출물」의 목록이 실제 파일과 맞는다
- [ ] 소스 코드와 빌드 설정, `spec.md`를 고치지 않았다

## 보고

- blueprint의 경로와 버전, 기준 spec 버전과 기준 헌법 버전.
- 만들거나 고친 부속 산출물. 손대지 않은 것이 있으면 그 사실.
- 개정이라면 무엇이 바뀌었는지와 등급, 지운 계약의 이름과 사유, 그리고 `doc revise`가 낸 뒤처진 breakdown. MAJOR나 MINOR로 뒤처졌으면 `/{{skill:breakdown}}`을 다시 실행해야 한다.
- spec에 없어서 넣지 않은 요구사항, spec이나 헌법에서 발견한 문제.
