# spec 단계

feature 하나의 spec을 만들거나 개정한다. spec은 사용자가 **무엇을** 필요로 하고 **왜** 필요한지를 정한다. **어떻게** 만드는지는 `/{{skill:blueprint}}`의 몫이다.

## 위치

- **산출물**: `docs/specs/{feature}/spec.md`와 `docs/specs/{feature}/checklist.md`. 산출물 디렉터리는 `.sdd-first/config.yaml`의 `docs_dir`을 따른다.
- **템플릿**: `.sdd-first/templates/spec.md`, `.sdd-first/templates/checklist.md`. 직접 복사하지 않고 `sdd-first doc new spec {feature}`로 만든다. 두 파일이 함께 만들어진다.
- **상위 문서**: `docs/prd.md`. 없어도 이 단계는 동작한다.
- **하위 문서**: 같은 디렉터리의 `blueprint.md`.

## feature 이름

1. 입력에서 feature 이름의 후보를 뽑는다. 기능을 대표하는 이름이며 영문 소문자, 숫자, 하이픈만 쓴다(예: `room-invite`). 입력이 한국어여도 이름은 영문이다.
2. 「현재 상태」의 목록에 같은 이름이 있는지로 신규와 개정을 가른다.
3. 사용자의 승인을 받는다. 승인 전에는 어떤 파일도 만들거나 고치지 않는다.
    - **신규**: 후보 이름을 보여 주고 승인을 받는다. 이 이름이 이후 모든 단계의 산출물 경로가 된다.
    - **같은 이름이 있음**: 기존 feature의 개정인지, 이름이 겹친 것인지 확인한다. 겹친 것이면 다른 이름을 받는다.

## 쓰는 기준

- 구현 방식(기술 스택, API의 형식, 코드 구조)을 쓰지 않는다.
- 개발자가 아닌 사람이 읽고 맞는지 틀린지 말할 수 있게 쓴다.
- 요구사항 하나는 그 문장만 읽고 통과와 실패를 판정할 수 있어야 한다.
- 입력에 없는 세부는 맥락과 일반적인 관행으로 합리적으로 정하고, 그렇게 정한 것을 4장 가정에 적는다.
- 다음 가운데 하나에 해당할 때만 `TBD:`로 남긴다. 그 선택이 범위나 사용자 경험을 크게 바꾼다. 결론이 다른 합리적인 해석이 여럿이다. 합리적인 기본값이 없다.
- 조건부 섹션(Figma 줄, UX 규칙, 주요 도메인)은 해당할 때만 쓰고, 아니면 제목이나 줄을 통째로 지운다. "해당 없음"이라고 남기지 않는다.
- 사용자 스토리의 ID(`US1`), 요구사항의 ID(`FR-001`, `UX-001`), 그 밖의 ID는 한 번 주면 바꾸지 않고 지운 번호를 다시 쓰지 않는다.

## PRD와 의존 항목

`docs/prd.md`가 있으면 읽는다. 없으면 이 절을 건너뛴다.

- 이 feature에 관련된 항목을 찾아 spec의 근거로 삼는다. 요구사항의 근거에 그 항목의 ID를 적는다.
- **의존 항목**: 이 spec이 의존하는 PRD 항목의 ID 목록을 제안하고 사용자의 승인을 받는다. 이 목록에 든 항목이 개정될 때만 이 spec이 뒤처진 것으로 판정된다. 빠뜨리면 그 항목이 바뀌어도 알 수 없고, 무관한 항목을 넣으면 쓸데없이 뒤처진다.
- 승인된 목록은 완료나 개정을 기록할 때 `--depends SYS-001,SCR-004`로 준다. 본문에 따로 적지 않는다.
- PRD의 항목 가운데 이 feature에 해당하는 것을 찾지 못하면 그 사실을 사용자에게 알리고, 의존 항목 없이 진행할지 묻는다. PRD를 고치지 않는다.

## 새로 쓰기

1. 「feature 이름」의 승인을 받은 뒤 `sdd-first doc new spec {feature}`를 부른다.
2. 「PRD와 의존 항목」을 따른다.
3. `spec.md`의 자리표시자를 제자리에서 채운다. 장의 순서와 제목은 바꾸지 않는다.
    - 입력에서 행위자, 행동, 데이터, 제약을 뽑는다.
    - **1장 사용자 시나리오**: 스토리마다 진입 조건, 흐름, 완료 조건, 테스트 시나리오, 엣지 케이스를 쓴다. 흐름을 정할 근거가 입력에 없으면 지어내지 않고 묻는다.
    - **2장 요구사항**: 기능 요구사항을 쓰고, 해당하면 UX 규칙과 주요 도메인을 쓴다.
    - **3장 범위**: 성공 기준과 다루지 않는 것을 쓴다.
    - **4장 가정**: 기본값으로 정한 것을 모두 적는다.
    - 다 채운 뒤 템플릿의 주석(`<!-- … -->`)과 남은 예시를 지운다.
4. 「미정 항목」의 절차를 따른다.
5. 「품질 검증」을 따른다.
6. 검증이 `pass`이면 완료를 기록한다. 의존 항목이 있으면 함께 준다.

    ```bash
    sdd-first doc complete spec {feature} --depends SYS-001,SCR-004
    ```

7. 「보고」를 따른다.

## 개정

1. `spec.md`를 읽는다. PRD가 있으면 「PRD와 의존 항목」에 따라 읽고, 기준 버전 뒤에 PRD에서 바뀐 항목이 이 spec과 어긋나는지 확인한다. 어긋나는 곳은 사용자에게 보고한다. 입력이 지목하지 않은 부분을 임의로 고치지 않는다.
2. 입력이 지목한 부분만 고친다. 이미 확정된 요구사항을 근거 없이 다시 쓰지 않는다. 이전 실행의 미정 항목 문답은 지우지 않는다.
3. 고치면서 `TBD:`가 생겼으면 「미정 항목」의 절차를 따른다.
4. 「품질 검증」을 따른다. spec을 고쳤으면 이전의 검증은 효력이 없다.
5. `sdd-first doc changes spec {feature}`를 불러 바뀌었는지 확인한다. 바뀐 곳이 없으면 기록할 개정이 없다.
6. 개정 등급을 근거와 함께 제안하고 사용자의 승인을 받는다.
7. 승인된 등급으로 개정을 기록한다. 의존 항목이 달라졌으면 함께 준다.

    ```bash
    sdd-first doc revise spec {feature} --grade minor
    ```

8. 「보고」를 따른다.

## 영향 없음 확인

PRD가 개정되어 이 spec이 뒤처졌지만 spec에 고칠 것이 없을 때의 흐름이다. 의존 항목만 고칠 때도 이 흐름을 쓴다.

1. PRD에서 기준 버전 뒤에 바뀐 항목을 읽고, spec의 어느 요구사항과도 어긋나지 않는지 확인한다.
2. 확인한 내용을 사용자에게 보여 주고 승인을 받는다.
3. `sdd-first doc confirm spec {feature}`를 부른다. 의존 항목을 고치려면 `--depends`를 함께 준다. spec의 버전은 그대로이고 기준 버전만 올라간다.

{{> revision-grade}}

spec에서의 기준은 다음과 같다. 하위 문서는 blueprint와 breakdown이다.

- **MAJOR**: 요구사항을 지우거나 뜻을 바꾼다. 사용자 스토리를 다시 정의한다. 범위를 줄이거나 넓혀 설계를 다시 해야 한다.
- **MINOR**: 기존 것을 둔 채 요구사항, 스토리, 엣지 케이스, 가정을 더한다. `TBD:`로 남겨 둔 것을 확정한다.
- **PATCH**: 표현을 분명하게 한다. 오타를 고친다. 근거의 링크를 고친다.

## 품질 검증

spec을 다 채웠거나 고쳤으면 `checklist.md`로 검증한다. 체크리스트가 `pass`이고 그 검증이 지금의 spec 본문에 대한 것이어야 CLI가 완료나 개정을 기록한다.

1. 개정이라면 `checklist.md`의 체크를 모두 `- [ ]`로 되돌리고 「발견한 문제」를 비운다.
2. 항목마다 `spec.md` 본문과 대조해 통과면 `- [x]`로 바꾼다. 통과하지 못한 항목은 spec의 해당 부분을 인용해 「발견한 문제」에 적는다. 통과하지 못한 것을 통과로 표시하지 않는다.
3. 통과하지 못한 항목이 있으면 그 문제를 사용자에게 보여 주고, 답을 받아 spec을 고친 뒤 2번부터 다시 한다. 세 번 되풀이해도 남으면 멈추고 남은 문제를 보고한다.
4. `sdd-first doc checklist {feature}`를 부른다. CLI가 체크를 세어 `pass`나 `failed`를 기록한다.
5. 이 명령 뒤에 spec을 한 글자라도 고쳤으면 2번부터 다시 한다. CLI는 검증한 뒤 본문이 바뀐 spec의 완료를 거부한다.

## 끝내기 전 확인

- [ ] 템플릿의 자리표시자와 주석이 남아 있지 않다
- [ ] 체크리스트가 `pass`이고 그 뒤 spec을 고치지 않았다
- [ ] PRD가 있다면 의존 항목을 사용자가 승인했다
- [ ] 개정이라면 기존의 ID와 미정 항목 문답이 그대로다

## 보고

- spec의 경로, 버전, feature 이름.
- 기준 PRD 버전과 의존 항목. PRD와 어긋나는 곳을 발견했으면 그 목록.
- 체크리스트의 결과(통과한 수와 전체 수)와 남은 `TBD:`의 수.
- 개정이라면 무엇이 바뀌었는지와 등급, 그리고 `doc revise`가 낸 뒤처진 하위 문서의 목록. MAJOR나 MINOR로 뒤처진 blueprint는 `/{{skill:blueprint}}`을 다시 실행해야 한다.
- 입력에 있었지만 이 단계의 범위가 아니라 하지 않은 일.
- 다음 단계: `/{{skill:blueprint}} {feature}`.
