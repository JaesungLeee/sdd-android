# clarify 단계

feature 하나의 spec을 따로 읽어, 설계로 넘어가기 전에 풀어야 하는 모호성과 상위 문서와의 어긋남을 찾는다. 건너뛸 수 있는 단계다. spec 직후와 blueprint 전에 쓰고, PRD가 개정되어 spec이 뒤처졌다고 나왔을 때 spec이 아직 맞는지 확인하는 데에도 쓴다.

spec의 품질 체크리스트는 spec을 쓴 에이전트가 형식과 완성도를 스스로 확인한 것이다. 이 단계는 그것과 별개로, 쓴 사람이 아닌 눈으로 다시 읽는다.

## 위치

- **읽는 것**: `docs/specs/{feature}/spec.md`, 있으면 `docs/prd.md`와 `docs/constitution.md`. 산출물 디렉터리는 `.sdd-android/config.yaml`의 `docs_dir`을 따른다.
- **쓰는 것**: 없다.

## 현재 상태

!`sh "$(git rev-parse --show-toplevel)/.sdd-android/bin/sdd-android" gate spec`

위에 판정 대신 명령이 글자 그대로 보이면 `sdd-android gate spec`을 직접 불러 확인한다.

이 단계는 판정으로 멈추지 않는다. 판정은 보고에 싣는다.

- 대상 feature에 `spec.md`가 없으면 시작하지 않고 `/{{skill:spec}}`을 먼저 실행하도록 안내한다.
- spec이 `작성 중`(`draft`)이어도 진행한다. 완료 전에 모호성을 찾는 것도 쓸모가 있다.
- `이 문서: prd에 대해 … 뒤처짐`이 있으면 「상위 문서와의 정합성」에서 PRD의 바뀐 항목을 반드시 본다.

## 1. 읽기

`spec.md`를 맨 위의 메타데이터까지 읽는다. `based_on`에 적힌 PRD의 기준 버전과 의존 항목(`items`)을 확인한다. PRD가 있으면 전체를 메타데이터의 `revisions`까지 읽고, 헌법이 있으면 읽는다.

## 2. 모호성 점검

아래 갈래마다 spec을 점검해 **분명함**, **부분적**, **빠짐** 가운데 하나로 판정한다. 이 feature에 해당하지 않는 갈래는 **해당 없음**으로 둔다.

| 갈래 | 보는 것 |
|---|---|
| 기능 범위와 동작 | 사용자의 목표와 성공 기준, 다루지 않는 것의 명시, 사용자 역할의 구분 |
| 도메인과 데이터 | 엔티티와 속성과 관계, 식별과 유일성의 규칙, 상태 전이, 데이터 규모의 가정 |
| 상호작용과 흐름 | 주요 사용자 흐름, 오류와 빈 상태와 로딩 상태, 접근성과 지역화 |
| 비기능 품질 | 성능, 확장성, 안정성, 관측 가능성, 보안과 개인정보, 규제 |
| 연동과 외부 의존 | 외부 서비스와 그 실패 양상, 데이터를 주고받는 형식, 버전에 대한 가정 |
| 엣지 케이스와 실패 처리 | 부정적 시나리오, 사용량 제한, 동시 수정 같은 충돌의 해소 |
| 제약과 절충 | 기술적 제약, 명시된 절충과 기각한 대안 |
| 용어와 일관성 | 같은 개념을 한 이름으로 부르는지, PRD의 용어와 같은지 |
| 완료 신호 | 요구사항과 완료 조건을 테스트로 판정할 수 있는지 |
| 자리표시자 | 남은 `TBD:`, 수치 없는 형용사("빠른", "직관적인", "안정적인") |

부분적이거나 빠진 갈래는 질문 후보가 된다. 다만 다음은 후보로 삼지 않는다.

- 답이 달라져도 설계나 검증 방법이 달라지지 않는 것.
- 구현 방식, 기술 스택의 비교, 작업을 나누는 방법에 대한 것. 이것은 blueprint와 breakdown의 몫이다.
- spec의 4장 가정에 이미 기본값으로 적혀 있고 그 기본값이 합리적인 것.

## 3. 상위 문서와의 정합성

PRD나 헌법이 없으면 해당하는 항목을 건너뛴다.

- **의존 항목과의 어긋남**: spec의 요구사항이 의존 항목으로 적은 PRD 항목의 내용과 어긋나는 곳을 찾는다. PRD의 플로우나 용어 정의와 다르게 쓴 곳이다.
- **빠진 의존 항목**: PRD 전체를 읽어, spec이 실제로 기대고 있는데 의존 항목에 없는 PRD 항목을 찾는다. 빠진 항목은 그 항목이 개정되어도 spec이 뒤처진 것으로 나오지 않게 만든다. 반대로 의존 항목에 있는데 spec이 기대지 않는 항목도 찾는다.
- **뒤처짐의 영향**: spec이 PRD에 뒤처져 있으면 `revisions`에서 기준 버전 뒤의 개정을 찾아, 바뀐 항목이 spec의 어느 요구사항에 영향을 주는지 본다. 영향이 없으면 "영향 없음 확인"으로 풀 수 있다고 보고한다.
- **헌법과의 어긋남**: spec의 요구사항이 헌법의 원칙을 어기게 만드는 곳을 찾는다. 원칙은 타협하지 않는다. 어긋나면 spec이 고쳐져야 하고, 원칙을 바꿔야 한다면 그것은 `/{{skill:constitution}}`의 일이다.

상위 문서 자체의 문제(PRD의 모순, 헌법의 모호함)를 발견하면 고치지 않고 보고한다.

## 4. 질문의 선별

질문 후보에서 **최대 5개**를 고른다. 한꺼번에 보여 주지 않는다.

- **영향이 크고 불확실성이 큰 것**부터 고른다. 설계, 데이터 모델, 작업의 분해, 테스트의 설계, 사용자 경험, 규제 대응을 바꾸는 것이 영향이 큰 것이다.
- 갈래가 치우치지 않게 고른다. 영향이 작은 질문 둘보다 영향이 큰 갈래 하나를 먼저 푼다.
- 질문은 **짧게 답할 수 있어야** 한다. 서로 겹치지 않는 선택지 2~5개에서 고르거나, 한두 마디로 답할 수 있게 만든다.
- 3장에서 찾은 어긋남 가운데 사용자의 결정이 필요한 것(spec을 고칠지, PRD가 틀린 것인지)도 질문으로 삼는다.
- 물을 것이 없으면 묻지 않는다. 그 사실을 보고하고 다음 단계로 가도 된다고 알린다.

## 5. 질문하기

**한 번에 하나씩** 묻고 답을 기다린다. 다음 질문을 미리 보여 주지 않는다.

```markdown
**질문 [N/전체]**: [그 자체로 뜻이 통하는 완전한 의문문]? (FR-003)

**왜 중요한가**: [답에 따라 무엇이 달라지는지 한 문장]

**권장**: [선택지] - [그렇게 권하는 이유 한두 문장]

| 선택지 | 내용 |
|---|---|
| A | … |
| B | … |
| 직접 | 다른 답을 짧게 적는다 |
```

- 질문은 주제 이름이나 요구사항 ID가 아니라 **의문문**이어야 한다. "수용 기기 목록 (FR-023)"은 질문이 아니다. ID는 물음표 뒤 괄호에만 적는다.
- 이 워크플로를 모르는 사람이 질문 줄만 읽고 답할 수 있어야 한다. 전문 용어는 같은 문장에서 풀어 쓴다.
- 선택지가 의미 없는 질문은 표 대신 **제안**을 적고 짧은 답을 받는다.
- 사용자가 "권장대로"라고 답하면 권장한 것을 답으로 삼는다. 답이 어느 선택지인지 분명하지 않으면 다시 확인하고, 이것은 새 질문으로 세지 않는다.
- 사용자가 그만하자고 하거나, 중요한 모호성이 모두 풀렸거나, 5개를 물었으면 멈춘다.
- 사용자가 지금 정할 수 없다고 한 질문은 **보류**로 적는다.
- 답을 받아도 spec을 고치지 않는다. 답은 6장의 보고에 모은다.

## 6. 보고

아래 순서로 보고한다.

1. **판정**: 「현재 상태」에서 대상 feature의 판정. spec의 상태와 PRD에 대한 뒤처짐.
2. **발견**: 3장에서 찾은 어긋남과, 질문으로 삼지 않았지만 알려야 하는 것. 발견마다 위치(요구사항 ID나 섹션), 무엇이 문제인지, 어느 단계에서 푸는지를 적는다.

    | ID | 종류 | 위치 | 발견 | 푸는 곳 |
    |---|---|---|---|---|
    | C1 | 빠진 의존 항목 | FR-004 | PRD의 SYS-002에 기대지만 의존 항목에 없다 | `/{{skill:spec}}` |

3. **문답**: 물은 질문과 받은 답. 보류한 질문은 따로 적는다.
4. **갈래별 요약**: 2장의 갈래마다 **분명함**(처음부터 충분했다), **풀림**(이번 문답으로 풀렸다), **보류**(질문했지만 정하지 않았거나 5개를 넘어 묻지 못했다), **남음**(부분적이거나 빠졌지만 영향이 작아 묻지 않았다), **해당 없음** 가운데 하나.
5. **spec에 넘길 입력**: 답과 발견을 spec에 반영하도록 `/{{skill:spec}}`에 그대로 넘길 수 있는 문장을 만든다. 반영할 것이 없으면 이 항목을 내지 않는다.

    ```text
    /{{skill:spec}} {feature} 다음을 반영한다: (1) FR-003의 … 을 … 로 확정한다. (2) 의존 항목에 SYS-002를 더한다. (3) …
    ```

6. **다음 단계**:
    - 반영할 것이 있으면 위의 입력으로 `/{{skill:spec}}`을 실행한다. spec은 그 단계에서 체크리스트 검증과 등급 승인을 거쳐 기록된다.
    - PRD에 뒤처졌지만 영향이 없으면 `/{{skill:spec}}`의 영향 없음 확인으로 기준 버전을 올린다.
    - 반영할 것이 없으면 `/{{skill:blueprint}} {feature}`로 간다.
    - 보류나 남음이 있으면, 그대로 설계로 가도 되는지 아니면 정한 뒤에 가야 하는지 의견을 덧붙인다.
