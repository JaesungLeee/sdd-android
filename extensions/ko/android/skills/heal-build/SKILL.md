# heal-build

빌드 실패와 Lint 실패를 고친다. 고쳐도 되는 범위가 좁다. **기계적 수정만 한다**: import 누락, 타입 불일치, null 안전성, 미사용 변수, 포맷. 의존성 변경과 로직 결함은 찾아서 보고만 한다.

{{> impl-input}}

인자에서 feature, 작업 ID, 경로, 실패의 요약을 읽는다. 요약만으로 위치를 알 수 없으면 해당 Gradle 태스크를 한 번 돌려 로그를 본다. 로그가 길면 서브에이전트에 분류를 맡기고 요약만 받는다.

{{> impl-scope}}

- 실패한 작업이 지정한 경로 안에서만 고친다. 실패의 원인이 다른 파일에 있으면 고치지 않고 `handed`로 보고한다.
- 테스트를 고치지 않는다. Lint 규칙을 끄거나 억제 주석(`@Suppress`, `// ktlint-disable`)을 더하지 않는다.

## 고치는 방법

1. 실패를 원인별로 나눈다. 같은 원인의 오류가 여럿이면 하나로 묶는다.
2. 원인마다 기계적 수정인지 판단한다.
    - **고친다**: import 누락, 잘못된 import, 타입 불일치와 캐스팅, null 안전성(`?.`, `!!`의 제거, 기본값), 시그니처 불일치(설계가 정한 쪽에 맞춘다), 미사용 선언, 포맷과 이름 규칙.
    - **고치지 않는다**: 의존성의 추가와 버전 변경, 설계와 다른 구조로 바꿔야 풀리는 오류, 로직 결함, 다른 모듈의 오류. `handed`로 보고한다.
3. 고친 뒤 실패했던 태스크를 한 번 돌려 본다. 빌드 실패를 고쳤으면 그 모듈의 Lint 태스크(`ktlintCheck` 등)도 함께 돌려 본다. 고친 줄이 Lint에 걸리면 다음 검증이 Lint 실패로 돌아와 시도 하나를 더 쓴다. 통과의 판정은 검증 스킬이 다시 하므로 여기서 통과를 선언하지 않는다. 돌려 본 결과가 또 실패면 그 결과를 보고에 적는다. 같은 자리에서 다른 시도를 반복하지 않는다. 한 번의 호출은 한 번의 시도다.

## 보고의 형식

```text
상태: fixed | handed
짚은 원인: 한 줄
시도: 무엇을 어떻게 고쳤는가 한 줄
바꾼 파일: 저장소 루트 기준 경로를 쉼표로
돌려 본 결과: 태스크와 결과
넘기는 사유: handed일 때. 의존성 변경 필요 | 로직 결함 | 범위 밖 파일 가운데 무엇인지와 위치
```
